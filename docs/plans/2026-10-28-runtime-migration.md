# Runtime migration plan: leaving Deno (Bun and Rust)

Status: draft for decision. Evidence: [`docs/explorations/runtime-migration/`](../explorations/runtime-migration/README.md) (experiment of October 2026, reports under `reports/`).

Assumption (not verified here): Deno is no longer maintained after the Cloudflare acquisition. The timeline sets the urgency but not the plan.

## Phase 0: common to both (do first, whatever the target)

Goal: make the migration verifiable, and fix what is broken independently of the runtime.

1. **Characterization suite.** Turn the experiment oracle (`docs/explorations/runtime-migration/run_cases.sh`, 39 cases) and `compat-tests` into a runtime-agnostic black-box suite: `CMD_MD` / `CMD_WL` variables select the binary under test. Extend the golden outputs (generated by the current Deno CLI) to every command and option, including write commands (assert on the resulting files). This is the safety net for both plans and the main reusable asset.
2. **Decide the behaviour changes explicitly** (one short ADR, then tests):
   - Markdown sections follow CommonMark 0.31.2: setext headings count, `#` inside code/HTML blocks never count, indented ATX (0–3 spaces) counts, CRLF works and is preserved. Open point: NBSP after `#` (the TS accepted it).
   - Frontmatter write policy: never rewrite on parse failure (refuse with an error), preserve key order; preserving comments and quoting is the target.
   - Normalize `write` quirks (forced blank line after the heading, `write ""` on an empty body).
   - Library API: is the `@dohzya/tools` JSR/TS API (`typescript-api.test.ts`) a supported product? Bun can keep it, Rust drops it.
3. **Fix the known bug on the Deno side now:** `md meta set` overwrites the whole frontmatter with `{}` when parsing fails.
4. **Pin versions of the Markdown parser and add the 80-file corpus** (`md-corpus/`) as a non-regression suite.
5. **Release schema stays:** one binary per tool and platform, Homebrew formulae unchanged in shape (URL + sha256 per platform). Plugins/skills only call `wl`/`md`, so they need no change as long as the CLI contract holds.

Exit criteria: suite green against the current Deno binaries; ADR accepted.

## Plan A: Bun

Principle: keep the code, replace the platform. Evidence: the experiment ported the slice in ~25 tool calls; `bun build --compile` works (all 5 targets cross-compile from one Linux runner).

| Phase                    | Work                                                                                                                                                                                                                                                                                                  | Exit criteria                                         |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| A1 Toolchain             | Bun via `mise`; `package.json` workspace + `tsconfig`; `tsc --noEmit` replaces `deno check`; formatter and linter replace `deno fmt/lint` (Biome or dprint + a rule replacing the `ExplicitCast`/no-`as` plugin; markdown formatting also needs a tool); `Taskfile.yml` tasks `test/validate` rewired | `task validate` runs on an empty-ish port             |
| A2 Platform layer        | Put the remaining direct `Deno.*` calls behind small adapters (`node:fs`, `node:path`, `node:child_process`, `process`), starting from `compat-tests/node-bun-compat.ts`; mechanical codemods                                                                                                         | no `Deno.` left outside tests                         |
| A3 Tests                 | Codemod `Deno.test` to `bun:test`; `@std/assert` kept through npm/JSR registry or replaced by `expect`; temp dirs via `node:fs`                                                                                                                                                                       | all unit tests green under Bun                        |
| A4 Dependencies          | `@std/yaml` (npm `@jsr/*` + `.npmrc`, or replace by `yaml`); zod mini from npm; `commonmark`; cliffy: check Bun support, otherwise `commander`/`citty` (+ completions, interactive select); dax → `Bun.$` or `node:child_process`                                                                     | `bun install` reproducible, lockfile committed        |
| A5 Markdown + YAML       | Markdown sections via the CommonMark AST + text splices (spike B Bun, 21 documented behaviour changes, 0 regressions); frontmatter edit by textual surgery (145 lines, 220/223 in the spike) with `yaml` as parser; avoid the private `_string_content` access (recompute setext start)               | corpus + properties P1–P6 green                       |
| A6 Packaging and release | `release.yml` uses `bun build --compile --minify --bytecode` for 5 targets (plus x64 baseline if needed); Windows/macOS smoke test on native runners; macOS signing/notarization; Homebrew formulae regenerated; decide **one multi-call binary** vs 4 binaries (4 × ~95 MB otherwise)                | release dry run on a tag, `brew install` on mac+linux |
| A7 Cutover               | Drop `deno.json`, `deno.lock`, JSR workflow; publish library to npm/JSR if kept; update `AGENTS.md`, `RELEASE.md`, `ARCHI.md` mentions, skills docs                                                                                                                                                   | Deno absent from the repo and CI                      |

Order of migration (leaf-first, each shippable): `recap` → `markdown-surgeon` → `dz-review` → `worklog`.

Costs and risks:

- Binary size ~95 MB per tool (same as Deno today), startup ~16–28 ms compiled (Deno: 287 ms).
- Bun is a single-vendor runtime: the same kind of risk that triggers this migration. Mitigation: keep the code Node-compatible (the `node:*` layer), so Node remains a fallback.
- Formatter/linter replacement is real work (Deno gave fmt, lint, check, test, compile in one tool); the `ExplicitCast` rule must be reimplemented.
- Cliffy compatibility on Bun is unverified.
- Bun's `commonmark` path depends on a private field; accept a recompute or pin the version.

Effort (rough, agent-assisted; code generation is cheap, verification and review dominate): small-to-medium. Order of magnitude: days to a few weeks calendar time, mostly A1, A4 and A6 decisions plus review of the codemods.

## Plan B: Rust

Principle: rewrite from the black-box contract, keeping the architecture (traits as ports). Evidence: the slice was written from the spec in one pass (1.1k lines, 39/39); spike B adds the AST-based sections (≈500 lines for 5 commands, 0 regressions, ~25× faster than TS on big files); `yaml-edit` / textual edit beats the current TS YAML handling.

| Phase                    | Work                                                                                                                                                                                                                                                                                                                                                                                              | Exit criteria                                |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| B1 Workspace             | Cargo workspace laid out as in [Workspace layout (2026-11-03)](#workspace-layout-2026-11-03) (`dz-encodings`, `md-manipulator` on `pulldown-cmark` + `yaml-edit` with textual fallback, `dz-cli-support`, one `-cli` crate per tool, `critique-{core,cli,wasm}`; dates with `jiff`); `mise` pins Rust; `cargo fmt`, `clippy -D warnings`, `cargo test`; Taskfile rewired; `deny`/`audit` optional | `task validate` green on skeleton            |
| B2 Test strategy         | Do **not** port 1026 unit tests 1:1: (a) the Phase 0 black-box suite is the contract, (b) differential testing in CI against a frozen Deno-built reference binary (random/generated workloads), (c) Rust unit tests only for domain rules and parsers                                                                                                                                             | suite runs against both binaries             |
| B3 `md`                  | Remaining commands beyond the spike: `empty`, `search`, `ref`/`resolve` (MRFI needs inline source positions: `pulldown-cmark` offsets or a small own scanner), `concat`, `meta`, `create`, magic expressions                                                                                                                                                                                      | md black-box suite 100 %                     |
| B4 `recap`               | Small, includes subprocess calls (`std::process`), YAML config                                                                                                                                                                                                                                                                                                                                    | suite 100 %                                  |
| B5 `dz-review`           | Review syntax scanner, session state, git subprocess, readline prompts                                                                                                                                                                                                                                                                                                                            | suite 100 %                                  |
| B6 `wl`                  | Largest (17k lines): task/trace/checkpoint model, git scopes and child worklogs, links, purge TTL, pager, interactive select (`dialoguer`/`inquire`), shell completions (`clap_complete`), many `--json` outputs; port by command group, read commands first (spike done), then writes (atomic writes, concurrency)                                                                               | wl suite 100 %, differential tests quiet     |
| B7 Packaging and release | Release matrix (native runners or `cargo-zigbuild`/`cross`) for the same 5 targets; binaries 1–3 MB; Homebrew formulae unchanged in shape; macOS signing; drop JSR library                                                                                                                                                                                                                        | release dry run, `brew install` on mac+linux |
| B8 Cutover               | Remove TS packages and Deno files; update docs, skills, `AGENTS.md` (TDD loop becomes `cargo test`), `ARCHI.md` (traits)                                                                                                                                                                                                                                                                          | repo contains no TS                          |

Order: `md` → `recap` → `dz-review` → `wl` (or start `wl` read commands early because the agents call `wl trace` constantly: startup 287 ms → ~1 ms is the visible win).

Costs and risks:

- Largest scope: ~38k source lines to reimplement plus semantics hidden in regexes, dates, YAML and Markdown edge cases; drift risk concentrates in `wl` writes (atomicity, concurrency, git scopes). The spike covered 3 read-only commands out of dozens.
- Maintainability by the owner: the codebase becomes Rust (the stated preference is TypeScript-friendly); agents write it, humans must still review it.
- Young crates in the path (`yaml-edit` 0.x, one maintainer): keep the textual fallback and a pinned corpus.
- Interactive features (select prompts) and completions need equivalents.
- JSR library API disappears (decision in Phase 0).
- No TS-style hot iteration: compile cycle 10–20 s clean, incremental faster.

Effort (rough, agent-assisted): large. Order of magnitude: several weeks to months calendar time, dominated by verifying behaviour parity on `wl`, not by writing code. An unassisted estimate from the first analysis was 20–30 person-weeks (±40 %).

## Comparison

|                                | Bun                                                | Rust                                                 |
| ------------------------------ | -------------------------------------------------- | ---------------------------------------------------- |
| Reuses existing code and tests | Yes (codemods)                                     | No (rewrite, tests rebuilt from the black-box suite) |
| Time to leave Deno             | Short                                              | Long                                                 |
| Binary size per tool           | ~95 MB                                             | 1–3 MB                                               |
| Startup of a CLI call          | ~16–30 ms                                          | ~1–3 ms                                              |
| Runtime dependency risk        | Single vendor (Bun); Node fallback possible        | None                                                 |
| Frontmatter editing            | `yaml` + textual surgery                           | `yaml-edit` or textual surgery                       |
| Markdown AST sections          | `commonmark.js` (private field workaround)         | `pulldown-cmark` (clean offsets)                     |
| Library API (`@dohzya/tools`)  | Can be kept                                        | Dropped                                              |
| Tooling to rebuild             | fmt, lint rule, markdown fmt                       | everything is native (`cargo`)                       |
| Main risk                      | Cliffy/tooling compatibility, vendor lock-in again | Behaviour drift in `wl`, scope and review load       |

## Possible sequencing (recommendation, to be decided)

1. Phase 0 now (valuable under every option, and it fixes a data-loss bug).
2. Bun migration to leave Deno quickly with the least risk (Plan A).
3. Keep Node-compatibility of the code so the runtime can still change.
4. Re-evaluate Rust for `wl` alone, only if startup time or the single-binary distribution proves to matter, using the Phase 0 suite and the differential setup as the contract.

The alternative is going straight to Rust, accepting the long path: it only makes sense if the owner wants Rust as the long-term language of these tools.

## Decisions (2026-10-29)

1. **Straight to Rust** (Plan B). Plan A is kept above as reference only.
2. The TypeScript library API of `@dohzya/tools` is dropped (it existed for Deno tooling).
3. The Markdown behaviour changes of Phase 0 are accepted (setext, HTML blocks, indented ATX, NBSP, CRLF).
4. One binary per tool, as today.
5. Formatter: with Rust, `rustfmt` and `clippy` cover the code. What remains is Markdown/JSON/YAML formatting (formerly `deno fmt`). Candidate: dprint, see below.

### Formatter evidence (checked 2026-10-29 on the 78 tracked md/json/yaml files, outside the exploration folder)

- `deno fmt` itself is built on dprint plugins. dprint 0.64.3 with `@dprint/markdown` 0.28.2 + `@dprint/json` 0.25.2 and `textWrap: never` would reformat only 2 files (one Markdown, one JSON with a different line width).
- Biome 2.6.3 with default settings would reformat 40 files (tabs by default, and it reformats embedded code blocks). Tunable, but a bigger diff and a different style.
- Not covered: YAML with dprint (the `pretty_yaml` plugin was not tried).

### Left over by Rust-direct (new decisions)

- `scripts/*.ts` (plugin version metadata, codex plugin validation, ~5 Deno scripts): rewrite as shell, as a Rust `xtask`, or drop.
- `packages/vscode/dz-review` (TypeScript VS Code extension, npm): stays TypeScript and needs its own lint/format and test setup; it contains a `deno-global.d.ts` to remove.
- `AGENTS.md` TDD loop and `TYPESCRIPT.md` / `ExplicitCast` rules become obsolete for `packages/tools`.

## Decisions (2026-11-03)

1. **Phase 0 status.** Step 1 (black-box suite) is done: `tests/blackbox/`, 1 395 cases green on the Deno reference (`md` 275 parity + 44 new-spec, `recap` 45, `dz-review` 568, `wl` 519). Step 3 (fix the Deno frontmatter bug) is abandoned: Deno is not touched anymore. Rust implements decision 10 of `docs/specs/markdown-sections.md` instead. Known Deno defects found while writing the suite are pinned as `parity` with a `note` in `case.json`; each one must be explicitly reproduced or fixed in Rust (list in `tests/blackbox/COVERAGE.md`). The ones that corrupt data (`wl scopes assign` leaving the child index without `version`, then the v2 migration overwriting task names) must not be reproduced.
2. **`dz-review` is renamed `critique`** (the project is a CriticMarkup extension for in-file review threads). Binary `critique`, state dir `.critique` (with a read fallback on `.dz-review` for existing sessions), `DZ_REVIEW_*` variables renamed, VS Code extension and skill `markdown-review-workflow` renamed at the same time so that extension and CLI stay aligned. The README must state precisely what is compatible with CriticMarkup. The black-box suite keeps its `dz-review` case names; a wrapper maps them to the new binary.
3. **Binary names are the long ones:** `markdown-surgeon`, `worklog`, `recap`, `critique`. `md` and `wl` are optional aliases (Homebrew: a separate `md` / `wl` formula that depends on the long one and symlinks it; archives ship a symlink, a copy on Windows). Docs, skills and `AGENTS.md` have to be updated to the long names or to document the aliases.
4. **Crates are named after what they are,** and `-core` is only added when a second consumer appears.

Rules:

- `md-manipulator` and `critique-core` do no I/O and must build for `wasm32-unknown-unknown`; CI builds `critique-wasm` and checks wasm vs native parity.
- Why `critique-core` is split from `critique-cli` while the other tools are not: the wasm build must not compile `clap` and friends (Cargo compiles all dependencies of a crate whatever the code reached, and feature unification can silently re-enable them), and ids/references must come from one compiled implementation shared by CLI and extension. The other tools have a single consumer; a `-core` can be extracted later at low cost.
- `hangul` has two consumers (MRFI payload and review timestamps), hence `dz-encodings`; it only keeps text codecs.
- Public crates are not published for now (private workspace); `md-manipulator` is the candidate when/if it is.

## VS Code extension (`packages/vscode/dz-review`)

Decision: keep the extension in TypeScript, and drive it with the Rust core compiled to WebAssembly, in process. Evidence: [`WASM-SPIKE.md`](../explorations/runtime-migration/reports/WASM-SPIKE.md).

- The extension imports `stable-review-id`, `reference-map`, `ref-core` and `runtime-config` from `packages/tools/dz-review` (which pull the markdown-surgeon parser and the section hash). Review item ids are written into files, so the editor and the CLI must compute the same ids.
- Hard requirement: **the extension and the `dz-review` CLI agree byte for byte.** Both are built from the same pure `core` crate; the `wasm` and `cli` crates contain no logic. Spike result: 80/80 corpus files and 996 generated ids identical between wasm and native.
- Where TS and Rust differ, the TS may be the wrong one: spike classification found only TS bugs (CRLF, CR, fences) and intended rule changes (setext, indented ATX, empty ATX, NBSP, HTML blocks), no Rust bug. One Rust bug was fixed along the way (V8 accepts `2023-02-31` and rolls it over).
- Numbers: `.wasm` 269 KB (256 KB with `wasm-opt -Oz`, 115 KB gzip), instantiation 1.6 ms, `outline` on 10 KB: wasm 0.42 ms / CLI spawn 2–3 ms / TS 3.8 ms; on 1 MB: 41 / 43–46 / 368 ms. No leak over 10k calls.
- Build: rustup (target `wasm32-unknown-unknown`), `wasm-bindgen` pinned with `=`, `esbuild --platform=node --format=cjs --target=node20 --external:vscode` replaces `deno bundle`. Fallback if wasm causes trouble: spawn the native CLI with stdin/JSON.

Design rules for the Rust workspace (apply from B1):

- The `core` crates are pure: functions on strings and values, no file, process or clock access (inject them). I/O lives in the bin crates only.
- `wasm` and `cli` are thin wrappers over the same `core` API; parity tests (wasm vs native on the corpus) run in CI.
- Positions cross the boundary as UTF-16 line/character for the extension; UTF-8 offsets stay inside the core.
- Regexes with lookahead are not available in `regex`/`regex-lite`: write those rules by hand or restructure them.
- Not yet verified: running inside a real VS Code host, `ref-core.ts` port, lone surrogates, bit-for-bit reproducible `.wasm`.

Extension work items: replace `deno bundle` by `esbuild`, drop `deno-global.d.ts` and the `../../../tools` imports in favour of the wasm package, keep its tests (`node --test`), add `ref-core` to the core crate.
