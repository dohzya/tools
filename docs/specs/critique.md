# critique (formerly dz-review)

Rust port of `dz-review` (`packages/tools/dz-review`), renamed `critique`. Crates: `critique-core` (pure: scanner, ids, reference map, timestamps, agent types, no I/O, builds for wasm32), `critique-cli` (binary `critique`, adapters for file system, git, clock, terminal), `critique-wasm` (JSON facade for the VS Code extension; the only place where positions become UTF-16). Its single entry point `reviewItems(file, text, mapJson | null)` returns `{ items, map }`: every item with its persistent id (assigned over all items before any filtering, like `list`, `session start` and `agent`), display id (shortest unique prefix over every id of the project: the reference map after assignment, all files, plus the file's own ids), kind, state, UTF-16 range, lines, metadata timestamp and conversation messages; `map` is the `reference-map.json` content to write, `null` when unchanged. File I/O stays in the extension, which locates `reference-map.json` with `stateDir(base, configured)` (see below).

Behaviour is pinned by `tests/blackbox/cases/dz-review` (557 `parity` cases recorded from the Deno tool) plus 54 `new-spec` cases (the table below). Run: `tests/blackbox/run.sh --ref rust --tool dz-review`. `task vscode:dz-review:parity` (CI) checks that the extension's `critique-wasm` agrees with the CLI over the repo's Markdown files (`packages/vscode/dz-review/test/cli-parity.js`: items, short ids, messages, reference map, references, timestamp conversion).

## Rename and state directory

| Item                                 | Before (`dz-review`)                           | Now (`critique`)                                  |
| ------------------------------------ | ---------------------------------------------- | ------------------------------------------------- |
| Binary, messages                     | `dz-review`                                    | `critique`                                        |
| State directory                      | `.dz-review` (Git root, else cwd)              | `.critique` (same placement)                      |
| Ignore file                          | `.dz-review-ignore`                            | `.critique-ignore`                                |
| Env variables                        | `DZ_REVIEW_STATE_DIR`, `DZ_REVIEW_IGNORE_FILE` | `CRITIQUE_STATE_DIR`, `CRITIQUE_IGNORE_FILE`      |
| `--state-dir`, `--ignore-file`, `-C` | unchanged                                      | unchanged (`--state-dir` beats env beats default) |

**No legacy fallback.** Outside the switch below, nothing named `dz-review` is read: neither a `.dz-review` directory or `.dz-review-ignore` file (even when `.critique` / `.critique-ignore` is absent) nor the `DZ_REVIEW_*` variables. The rule lives in `critique_core::state::locate`: the first non-blank configured value (`--state-dir`, then `CRITIQUE_STATE_DIR`; a relative path is relative to the cwd), else the default name under the Git root (else the cwd; the ignore file is always cwd-relative). The default state directory and the configured one are ignored when discovering files. The VS Code extension uses the same function (`stateDir` in `critique-wasm`) for its reference map, with its `dzMdReview.stateDir` setting before `CRITIQUE_STATE_DIR` and the workspace folder as cwd.

**Legacy identity switch.** `CRITIQUE_COMPAT_DZ_REVIEW=1` (any value but empty or `0`) makes the binary behave as `dz-review`: name in messages and `agent-instructions`, `.dz-review` / `.dz-review-ignore` defaults, `DZ_REVIEW_STATE_DIR` / `DZ_REVIEW_IGNORE_FILE` read after their `CRITIQUE_*` counterparts. It exists so that the legacy suite (cases written against `dz-review`) runs unchanged; `tests/blackbox/refs/rust/dz-review` sets it unless a case sets the variable to an empty string, which is how the `new-spec` cases `global/new-*` test the real defaults.

## Ids

Unchanged and byte-identical to the TS values (they are persisted in user documents): `rvw_` + base62 (`0-9A-Za-z`) of FNV-1a 64 over the UTF-16 code units of `file\0kind\0anchor` (anchor truncated to 160 UTF-16 units, so a truncation inside a surrogate pair still hashes like the TS). Timestamps use the other base62 alphabet (`0-9a-zA-Z`). `critique-wasm` and the CLI call the same functions; a test pins the historical vectors. One deliberate exception: the value of a `ref%ts:` prefix is stripped, like the other review timestamps, from the text anchor (items without their own timestamp), from the first message an untimestamped conversation is anchored on, and from `rawHash`, so they no longer depend on the timestamp format; such an item gets the id the TS gives to the same text with a bare `ref:` (a reference map keeps an id assigned before).

## References

Every `ref` subcommand (`check`, `list`, `show`, `snapshots`) resolves a target path the same way, in Deno (`packages/tools/dz-review/resolve-target-file.ts`) and in Rust (`target_file` in `crates/critique-cli/src/commands/refs.rs`); `ref list --json` prints the result as `targetFile`:

- an absolute path is kept as is;
- a path starting with `./` or `../` is relative to the folder of the document holding the reference;
- any other path is relative to the Git root, or to the document's folder outside a Git repo.

So in `sub/doc.md` of a repo, `ref: source.md:6` points at `source.md` at the root and `ref: ./source.md:6` at `sub/source.md`. Pinned by `ref/list-in-subdir-json` (no Git) and `ref/list-in-subdir-git-json` (Git: bare, `./` and `../` paths).

## Quirks kept on purpose

- Items collected as annotations have no `roles`: `--open`, `--wip`... without `--conversations` never match a conversation (every annotation-collected item counts as `handled`); with `--conversations` the real status is used.
- Selection flags (`--pending`, `--open`, ..., `--*-conversations`) are resolved in a fixed order, not left to right (the TS rebuilt argv from an options record); likewise `--context` then `--context-before/after`.
- `{?? a ?}` (closed by `?}`) is a conversation for the conversation collector but not an annotation.

## Not ported / backlog

- `Date` strings other than ISO forms in `now --date` (V8 legacy parser).
- Interactive `review` on a terminal (line editing); only the stdin-driven mode is implemented and tested.
- Ignore-file discovery sorts names bytewise (TS used `localeCompare`).

## To validate

1. `--remove` lives on `agent apply` (where `--replace` is), not on the interactive `review`, which already has its own delete answer.
2. `ref check` and `~<review id>`: any `~xxx` that is not a valid MRFI is refused like every invalid reference (pinned by `cli.test.ts` in the TS); the skill documentation (`review-syntax.md`, `mrfi.md`) was wrong and now shows the `~<mrfi>` form generated by `md ref`. A review id is still read after a second `~` (`file~~<id>`), a parser quirk kept from the TS and not documented as syntax (`ref/check-review-id-*`, `ref/new-check-review-id-*`).
3. Effect of the `rawHash` change on a session started with an earlier build: the snapshot holds the old raw-byte hash, so a multi-line item of a CRLF or CR file reads as modified once (LF files are unchanged: the hash of LF text is byte-identical). Restarting the session (`session start --force`) clears it.
4. `ref%ts:` prefixes are converted and counted by the format detection (`--format-info`, the snapshot `timestampFormat`, the `session done` drift guardrail) like the markers and annotations. A file whose only timestamps are `ref%` prefixes (its items untimestamped) is no longer `none`: `session done` restores it to the prefixes' format, items stamped by `session start` included, where it used to leave the file ISO (`session/new-done-restores-ref-prefixes`). A file whose `ref%` prefixes use another encoding than its items can fall below the 90 % threshold and become `mixed` (left ISO after the session).
5. Ids and `rawHash` of items embedding a `ref%ts:` prefix change once (its value is no longer hashed): without a reference-map entry such an item without its own timestamp, an untimestamped conversation whose first message embeds the prefix included (decided 2026-11-20), gets a new id; a session started with an earlier build reads such items as modified (`session start --force` clears it).
