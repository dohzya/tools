# Rust crate shortlist for the dz-tools migration

Date: 2026-10-27. Legend: **[V]** = verified online today (crates.io API / GitHub API), **[M]** = from memory, not re-verified, **[S]** = measured in the spike. Download counts are all-time / last-90-days as reported by crates.io **[V]**.

## Spike results (copy in `experiment/rust-crates/`, original untouched except its `target/` was rebuilt)

Oracle: **39/39** after each step (regex-lite+jiff, then +clap).

|                                                           | Original | Spike (regex-lite + jiff + clap)                                        |
| --------------------------------------------------------- | -------- | ----------------------------------------------------------------------- |
| Source lines (main+md+wl, excl. tests)                    | 1124     | 1074 (-50: wl.rs -79, main/md +29 for clap derive)                      |
| Release binary (LTO, strip)                               | 730 KB   | 1 267 KB (968 KB before clap; 2.63 MB if `regex` replaces `regex-lite`) |
| Startup, `md read`, mean of 50 spawns (python subprocess) | 0.68 ms  | 0.81 ms                                                                 |
| Clean release build                                       | 9.7 s    | 18.4 s                                                                  |

Net: the crates removed ~80 lines of fragile code (the date arithmetic and the string scanning) but the line delta is modest because the original was already compact; the real benefit is correctness surface (leap seconds, offsets, fractional seconds now handled by jiff; clap gives help/completions). Cost: +537 KB, +9 s clean build, +0.1 ms startup (spawn noise level).

## What stays hand-rolled, and why

- Section scanner (frontmatter end, fences, header rule, line ranges, `hash8`): it encodes the TS tool's exact, non-CommonMark rules; a CommonMark parser would diverge.
- `short_id`, rendering, JSON shaping: domain logic, no crate applies.
- Only `header()` was left as-is in the spike for the same reason (a regex would work but gains nothing).

## Risks

1. YAML: `serde_yaml_ng` is stale (last release 2024-05); `yaml-edit` is the only lossless editor, young and unproven; plan a splice-based fallback for frontmatter writes.
2. Weight: clap + jiff + regex cost ~540 KB and +9 s build; avoid full `regex` and `gix`; consider `lexopt` if size matters more than ergonomics.
3. `regex-lite` semantics differ from JS/`regex` (Unicode classes); keep parity tests.
4. Unverified here (memory): comrak/pulldown-cmark offset APIs, jiff ISO duration parsing, `serde_path_to_error`, winnow footprint.
